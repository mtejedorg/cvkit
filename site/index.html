Career tooling that is not allowed to lie.

cvkit is three Claude Code skills with one rule: nothing is claimed that its source doesn't back. One tailors your CV and cover letter to a posting, one keeps your LinkedIn profile and posts consistent, one builds your portfolio and project sites. cv-builder and linkedin work from one private fact file about you and stop and ask when they would have to claim something it doesn't back up; portfolio works from the repo's own documents and leaves out what they don't cover. Each reviews its own work before you see it.

The kit

Three skills, one rule

Open Claude Code in the repo and say what you need. The skill that matches takes over, reads your profile, and shows you the text before anything is sent, pasted or published.

CV

cv-builder: build CVs and cover letters

Give it a job posting. It rates the fit, asks about every requirement your profile doesn't back, drafts a CV, cover letter and project portfolio, rewrites them so they don't sound like a template, has a fresh reviewer critique them, then compiles and verifies A4 PDFs, with a public version that has no phone number.

Design philosophy

Six rules the whole kit is built around

AI-written applications tend to fail in two ways: they invent things, and they sound like every other AI-written application. Each rule below targets one of those failures, or the checks that catch them. cv-builder follows all six. linkedin applies them to its sections and posts. portfolio applies the ones that fit (no invention, human tone, checked output) to the repo's own documents.

01

No hallucination

Every skill, title and number must exist in the candidate profile. If the posting needs something the profile lacks, the skill halts and asks you instead of assuming.

02

Humanized, not detector-evasion

A direct rewrite pass removes template-sounding language while keeping every fact identical. No translation chains, no external APIs, no attempt to hide that AI was used.

03

Fresh-context review

A second agent with no memory of the drafting critiques the result against the posting, so it catches missed keywords and weak framing the drafter has stopped seeing.

04

Verified PDFs

Every PDF is checked for page count, a clean text layer and literal contact details, so an applicant tracking system can actually read it. Then it is inspected by eye. The site skill has its own checks: manifests, a privacy scan and image sizes are verified before anything is published.

05

The profile learns

Every answer you give to a clarification question is written back to your profile in your own words. A "no" is kept as a confirmed gap, so it is never claimed later and each application starts from better facts than the last.

06

Lead with proof

The profile ranks your strongest verifiable claims and names a positioning profile per kind of role. Each run picks three proof points for the posting and puts them in the summary, the first bullets and the letter's opening, within a two-page budget.

The shared fact file

One profile, written once, believed by the CV and LinkedIn skills

The candidate profile is a Markdown file you keep outside this repo. cv-builder and linkedin are allowed to believe nothing else, and its headings are a contract they read. The portfolio skill believes only the project repo's own documents and the software itself.

What it holds

  • Positioning profiles: one per kind of role, each with a short summary and three leading proof points
  • Ranked proof points, with the evidence behind each
  • Skills with a depth level: production, working, academic, evaluated, supervised
  • Verified metrics inside each role, with how and when each was confirmed

How the skills use it

  • Depth decides the wording: anything below working is a gap the skill must ask about
  • A Not claimable list holds what you confirmed you don't have, so it is never claimed or asked again
  • Preferences set how many numbers you like, the output language and the photo rules
  • Every answer you give is written back to the file, and you see the exact lines

The profile, your applications log and your generated files live in a workspace folder or private repo. Once you list your own patterns and enable the pre-commit hook, a commit containing any of them is blocked, so the public skill repo stays free of personal files.

cv-builder · How it works

Draft, humanize, review, score, compile, verify

The CV skill runs these phases in order. The red and green tags mark where it stops for you or checks itself.

  1. 0

    Workspace

    Finds your private workspace (profile, applications, log) through an environment variable or a gitignored config file, so the public skill repo never holds a personal file.

  2. 1

    JD analysis, fit check & clarification Halts & asks you

    Saves the posting as JD.md, reads it against your candidate profile and rates the fit (location, permit, seniority, domain years, language). If the fit looks unlikely it says why and asks before going on.

    It then cross-references the posting with your profile. Every item the profile doesn't back, hard requirement or soft skill, is a question for you, asked before a single word is drafted. Then it names the positioning profile and the three proof points it will lead with.

  3. 2

    Drafting

    Writes the CV, cover letter and project portfolio in Markdown, then self-critiques for truthfulness, bullet order and structure. No PDF yet: compilation happens once, at the end.

  4. 3

    Humanization pass Facts frozen

    Rewrites for natural variation against a checklist. Style only: no fact, number, date or meaning may change.

  5. 4

    Reviewer subagent Fresh eyes

    A subagent with a clean context gets the posting, the drafts and the relevant profile excerpt, and returns a structured critique. Its feedback is applied, and the humanization check is re-run on anything it changed.

  6. 5

    Gates & score 2 gates + 0–100

    Two pass/fail gates (format, truth), then a score where half the points are evidence: how many of the posting's must-haves your profile backs and the CV shows. An invented claim found here sends the run back to phase 1, not into a quiet deletion.

  7. 6

    Compile & verify PDFs Automated + visual

    Renders the Markdown onto real A4 pages (two for a CV, one for a letter), builds a phone-less public variant on request, runs the verifier, and reads the result to confirm nothing is cut off or misaligned.

  8. 7

    State update Writes your profile

    Every answer you gave, from phase 1 or from questions the reviewer or scoring raised later, is saved to the candidate profile in your own words. A "no" goes under Not claimable. Nothing is inferred, and the exact lines added are shown to you. This runs even after short commands like an ATS-only check.

  9. 8

    Interview prep Optional

    On request, a STAR-method prep pass based on the posting and the final documents.

cv-builder · Rules 01 & 05 in action

Ask before lying, then remember the answer

When the posting asks for something the profile doesn't contain, the skill does not stretch the truth. It stops, asks, and keeps what you told it.

 phase 1 · jd analysis

you › Tailor my CV for the Senior Backend Engineer posting at Northwind Labs.

skill › I compared the posting with your profile.

  • Matched: Go, PostgreSQL, AWS, mentoring
  • Not in your profile: Kubernetes in production

HALT. The posting lists Kubernetes as required. Your profile mentions Docker and AWS ECS, but not Kubernetes. Do you have hands-on Kubernetes experience? I won't add it unless you confirm.

you › Only Docker and ECS, no Kubernetes.

skill › Understood. The CV will feature Docker and ECS and leave Kubernetes out. Drafting now.

…and later, in phase 7, it writes the answer backThe profile is the skill's memory. Whatever you confirmed is saved, so the next application starts from it.

skill › Saving what you told me to _private/candidate_profile_alex-rivera.md:

## Not claimable+ Kubernetes — confirmed 2026-03-14 (Northwind Labs posting) — "Only Docker and ECS, no Kubernetes."

skill › 1 entry added. Kubernetes is now under Not claimable, so I won't claim it in any CV. If that changes, tell me and I'll update it.

All skills · Rule 02 in action

Humanizing means "don't sound like a template"

The pass changes how a true sentence is said, never what it says.

Before

Orchestrated a seamless migration of a Python monolith into 6 services on AWS (ECS, RDS PostgreSQL), leveraging modern tooling to reduce deploy time from 50 minutes to 9.

After

Split a Python monolith into 6 services on AWS (ECS, RDS PostgreSQL), reducing deploy time from 50 minutes to 9.

Illustrative before/after, written for this page. Highlighted in red: phrases the checklist flags. In green: facts that must not change.

What the pass looks for

  • Banned stock phrases ("proven track record", "seamless", "leverage" as a verb…)
  • Consecutive bullets opening with the same verb
  • Every sentence the same length and shape
  • More than one "moreover / furthermore / additionally"
  • Em-dash overuse
  • No fact, number, date or title changed
Why not a detector-evasion pipeline? Some humanizer tools push text through chains of machine translation to fool AI-content detectors. That was rejected here: nobody scans a CV for detector signals (a recruiter or a text parser reads it), and every extra translation hop risks drifting a tool name, a metric or a date in a document where each claim must stay true. cvkit never tries to hide that AI helped.
cv-builder · Rule 03 & scoring

A second opinion, and a score with a penalty

The reviewer gets, inline

  • The job posting, verbatim
  • The drafted CV, cover letter and portfolio
  • Only the profile sections relevant to this posting
  • The ATS score, if already computed

The reviewer returns

  • Keywords the profile supports but the draft missed
  • True claims stated too vaguely
  • Language that still reads as templated
  • The same metric phrased two different ways across documents

The reviewer is told it is reviewing, not researching the company or inventing anything about the candidate. Suggesting a claim the profile lacks is treated like any other gap: it goes back to you as a question.

50Evidence
20Placement
15Content
15Keywords
Evidence coverage: each ranked must-have counts when the profile backs it and the CV shows it with evidence.
Placement: the three leading proof points in the summary and first bullets.
Content quality: action + what + how + measurable result, checked against the profile.
Keywords: real posting terms the profile supports. Gaps are acknowledged, never stuffed.
Truth gate: one invented skill or claim, or one assumed without asking, fails the run: it goes back to phase 1 and asks you. The format gate (single column, standard headings, order, length) is pass/fail too.
cv-builder · Rule 04 in action

Output that is checked, not assumed

Below is a real PDF compiled and verified by the toolchain. The fictional candidate's Markdown was written by hand for this page, so it shows the output stage, not the drafting.

  1. Markdown → HTML with a fixed template (single column, standard font, a flexbox header).
  2. Headless Edge → PDF on real A4 pages, with break rules that keep a role title with its first bullets. A --public build strips the phone number for anything that goes online.
  3. Verifier enforces the page cap (two for a CV, one for a letter), checks the text layer for garbled characters, that the sections appear in order, and that the contact details are literal text (or, for a public build, that the phone is absent).
  4. Privacy check scans every tracked file for the candidate's own patterns before a commit can land.
  5. Visual read confirms nothing is cut off and the header renders as a proper row.
linkedin · Keep it true

A LinkedIn profile that says what your profile can prove

LinkedIn has no write API for a personal profile, so the skill works through the browser and produces paste-ready text, section by section, each within the platform's limit. A record of what is live means the next change starts from the truth.

audit

Compares the live profile with your fact file. Flags any claim the profile doesn't back, numbers that aren't verified metrics, stock phrases, sections over their limit and missing proof points. Then the reviewer personas read it.

sync

Rewrites the flagged sections (or all, on request) from the positioning profile you choose. The headline and the first lines of About carry your strongest proof. Each section gets its own file with a character count, and a change list shows old against new.

post

Drafts a post from a source you name: a project, a repo README, a CV folder or an event. You get three variants with different hooks, each with its character count, a suggested real image (a capture, never a generated one) and the facts it relies on.

message

A reply to a recruiter, a connection note (kept under the 300-character cap), a follow-up after applying or a thank-you after an interview. Short, specific, one ask. Your phone number is left out unless you say otherwise.

settings

Recommends open-to-work visibility, what contact information to expose and which items to feature, as a checklist for you to click through. Settings change only on an explicit yes, one at a time.

You stay in control of the page. The skill opens your public profile in Claude's built-in browser pane (desktop app) and reads it. If LinkedIn asks for a login, you sign in yourself; the skill never types credentials. By default you paste the approved text. Only if you ask it to apply an edit does it fill one section's edit dialog, show you the result and wait for a yes before saving. There is never a bulk save. Without a browser, a LinkedIn data export works as the source.
portfolio · Sites on GitHub Pages

A portfolio hub and a site for every project

One skill, two roles. The hub is your personal site at <you>.github.io, with one card per project. A project is any repo that publishes its own site at <you>.github.io/<repo> plus a small portfolio.json manifest. The hub never scrapes a project: it reads the manifest.

Commands

  • init: scaffold a hub, or a project site with three pages, its manifest, a capture helper and the Pages workflow
  • sync: rebuild a project's pages from the repo's own docs, or refresh the hub's cards from every project's manifest
  • check: validate manifests, run the privacy scan, check banned phrases and image sizes, then the reviewer personas
  • publish: copy the site into the hub repo and commit. Pushing stays with you

Three rules

  • Only real facts and real images. Screenshots are captures of the real thing, concept art is labelled concept art, and a fact the repo doesn't document is left out
  • Nothing personal leaks. No phone numbers anywhere, and any email is assembled by script so scrapers don't read it
  • Nothing is hardcoded. Owner and repo come from the git remote, so a fork works with no edits

The skill never creates a repo, never pushes and never switches Pages on. It tells you the one Settings step (Pages, Source "GitHub Actions") and the workflow deploys on your push.

All skills · Reviewer personas

A panel of readers sees it before you do

Every skill puts its output in front of reviewers who read as the people it is written for. Three ship with the kit, and you can add the ones that matter most to you.

Recruiter screener

Spends under a minute per CV across dozens of open roles and decides whether it goes to the hiring manager. Reviews CVs, letters, LinkedIn and sites.

Applicant-tracking parser

Not a person: the parser inside a tracking system. Anything it can't read as plain text under a standard heading doesn't exist for it. Reviews CVs.

Generic hiring manager

Reads the shortlist between meetings, wants something shipped and specific, and can tell a real contribution from a team's. Reviews CVs, letters, portfolios, LinkedIn and sites.

Say "create a persona for <role or company type>" and the skill drafts one from your positioning profiles and past postings, into your private folder. Each skill runs the personas that review its kind of output. Findings that several personas share become edits; a finding from one persona is applied when it costs the others nothing, and reported to you as a trade-off when it does. Facts never change in this step.

Use it

Run it for yourself

It is designed to be forked and used by anyone, not just the author. The skills use the toolchain in this repo, so clone the whole repo rather than copying a single skill folder.

  1. Fork or clone the repo and install the dependencies: Python 3.10+, pip install PyMuPDF markdown pytest Pillow, and Microsoft Edge for headless PDF rendering.
  2. Choose where your private data lives. Either inside the clone (_private/ and _generated/ are gitignored), or in a separate private folder or repo that a gitignored cvkit.config.json (copy cvkit.config.example.json) points to, or that the CV_WORKSPACE variable names. The second keeps the public repo free of any personal file.
  3. Write your candidate profile from the template in templates/, as _private/candidate_profile_<your-name>.md: positioning profiles, ranked proof points, skills with a depth level, verified metrics, what you can't claim and your preferences. cv-builder and linkedin believe nothing else.
  4. Turn on the privacy check. List your email, phone spellings and private file names in _private/privacy_patterns.txt, then enable the pre-commit hook once with git config core.hooksPath .githooks. Run python -m pytest -q to confirm the toolchain works on your machine.
  5. Open Claude Code in the folder and ask. For example: "Tailor my CV for <posting URL or pasted text>", or "Audit my LinkedIn profile against my profile". Answer the questions about gaps; the skill won't draft until you do, and it saves your answers so it doesn't ask twice. To build a project page for another repo, copy .claude/skills/portfolio to ~/.claude/skills/ (every repo) or into that repo's .claude/skills/, open Claude Code there and say "Make a project page for this repo".
  6. Collect the results in _generated/<Company_Role>/ for applications, _generated/LinkedIn/ for profile text and posts, and in the repo's site folder for sites.
Transparency

What it does not do

  • It is AI-assisted writing. The drafting is done by a language model, and it can still make mistakes. The profile gate, reviewer and scoring reduce that risk but do not remove it, so read every document before it goes out.
  • It is only as honest as your profile. The skills trust the fact file. If the file overstates something, the output will too. Because your answers are written back to it, a wrong answer persists until you correct it, which is why the skill shows you each change.
  • The score and the fit verdict are heuristics. They catch problems and flag likely screens (location, permit, seniority), but they are not a measurement from any real applicant tracking system. Each application's score and outcome are logged so you can check whether they predicted anything.
  • Humanizing is not concealment. It exists so the text reads like a person wrote it, not to disguise AI involvement.
  • It never posts or publishes on its own. LinkedIn has no write API for a personal profile, so you paste the text, or approve one edit at a time in the browser if you ask for that. The site skill commits to your hub checkout but never creates a repo, pushes or enables Pages; you do those steps.
  • Tested on Windows. PDF rendering needs Microsoft Edge. The script looks for it at standard macOS and Linux paths too, but that is untested.
  • No guarantees. A well-tailored, truthful CV helps. It does not get you an interview on its own.
